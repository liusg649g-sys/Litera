## 1. 目的与适用范围

本规范规定 Litera
从构建、配置、启动、观测、发布到回滚和数据恢复的基本要求，确保版本可追溯、环境可区分、故障可发现、数据可恢复。

本规范适用于前端、后端
API、数据库、PDF/图片等文件存储，以及已接入或未来接入的 AI
服务。当前本地开发、预览与独立 API 环境按各自配置运行；历史记录中的
5177、5180、8002、8003
仅作为历史环境记录，不应被写死为所有部署环境的固定端口。是否使用
Docker/Compose，以当前仓库和团队选定的部署方式为准；本规范不要求为日常本地验收额外启动
Docker。

## 2. 部署原则与环境隔离

1.  开发、测试、预览和生产环境必须明确区分；环境的数据库、文件目录、账号、密钥和日志不得混用。
2.  环境差异应通过配置注入，不应通过手工修改源代码实现。
3.  同一版本的构建产物应尽量保持一致，通过配置切换环境；未经记录的临时补丁不得作为正式发布版本。
4.  运行环境、启动命令、端口、依赖、数据目录、健康检查和停止方式必须记录在
    README 或运维文档中。
5.  预览环境不得被默认视为生产环境；测试不得默认连接含有真实业务数据的本地实例。
6.  所有运维操作应遵循最小权限原则。涉及删除数据、迁移、覆盖、清理文件卷或重建数据库的操作必须事先确认目标环境并具备恢复方案。

## 3. 可复现构建与版本身份

每次可交付构建记录源码分支/提交及未提交差异、应用版本/时间、锁文件与产物身份、部署配置/迁移版本和实际验证结果。不能仅用HEAD描述含未提交改动的本地构建。

依赖应使用锁定文件或精确版本约束。重新生成依赖清单前，应确认直接依赖与运行时依赖完整，避免出现开发环境能运行、干净环境无法构建的情况。

构建上下文必须排除 `.env`、数据库文件、上传的
PDF、用户资产、缓存、日志和其他运行时数据。不得把私有文献、数据库或密钥复制进镜像或静态发布目录。若采用
Docker，镜像应使用明确版本标签；重要发布应记录镜像摘要或其他不可变身份。不得只使用
`latest` 作为回滚依据。

每次发布前应在干净环境验证依赖安装、前端构建、后端启动和基本健康检查。配置文件存在不等于部署成功。

## 4. 配置与密钥管理

1.  配置项应按用途集中管理，并提供不含秘密的示例文件。
2.  密钥、数据库口令、会话签名材料及 AI 服务 API Key
    只能通过受控环境变量或受保护的密钥管理方式注入，不得提交到
    Git、写入前端代码、打包进静态资源或输出到日志。
3.  环境变量名称、用途、是否必需、默认值及安全要求必须有文档说明；真实密钥不得出现在示例文件中。
4.  启动时应校验必需配置。生产模式下缺少安全配置时应明确失败，不得静默使用开发默认值。
5.  密钥轮换后应验证新配置生效，并明确旧密钥撤销步骤；发生泄露时应立即轮换并检查相关日志。
6.  修改配置后，应记录影响的环境、重启要求及验证结果。

## 5. 启动、健康检查与优雅停止

启动流程必须明确依赖顺序，包括配置校验、数据库连接、迁移策略、文件目录检查、后台任务启动和服务监听。数据库迁移及文件清理等启动副作用必须在运维文档中说明。

健康检查目标区分：

- **存活检查：** 判断进程是否仍在运行。
- **就绪检查：** 判断服务是否已准备好接收请求，包括必要依赖是否可用。

当前仅有统一健康端点，分离探针是待落实要求。

健康检查不得泄露密钥、数据库连接串或内部堆栈。依赖不可用、超时和恢复场景均应进行验证。部署编排若支持健康检查，应避免仅因短暂启动延迟就反复重启服务。

停止服务前应停止接收新请求，并在可行时等待在途请求完成；后台任务应能有序停止。必须验证停止和重启不会导致文件、数据库事务或任务状态不一致。

## 6. 日志、指标与告警

日志应便于按请求追踪，并至少包含时间、级别、模块/服务、请求标识、操作结果及必要的耗时信息。新增或改造日志须采用单行JSON结构，至少包含timestamp、level、module、requestId、result；当前文本日志尚未统一，列为待落实，不为文档审查改业务代码。

日志要求：

- 不记录密码、令牌、Key、完整会话或私人文献正文。
- 保留错误类别和请求标识，不向用户返回堆栈。
- 明确位置、轮转、期限、容量监控和访问权限。
- 跨服务请求关联须有实际传播机制，不能只因返回X-Request-ID就宣称全链路贯通。

运维至少应规划以下指标：请求量、错误率、响应延迟、数据库/文件存储连通性、磁盘使用量，以及
AI
功能启用后的模型调用次数、耗时和失败率。每个告警必须有触发条件、责任人和处置动作。指标与告警尚未接入时应明确标注为待建设，不得声称已实现监控。

## 7. 数据库迁移与兼容性

1.  每项数据库结构变更必须有迁移脚本、升级说明、影响分析和验证用例。
2.  生产或含重要数据的环境迁移前必须完成可验证的备份，并确认备份可恢复。
3.  优先采用"扩展---迁移---收缩"顺序：先增加兼容结构，再迁移/双写或切换读取，最后在确认旧版本不再依赖后删除旧字段。
4.  发布前应明确迁移由哪个进程或运维人员执行，避免多个实例同时执行不受控的迁移。
5.  迁移完成后必须验证关键表、约束、索引、记录数、关联关系及核心读写路径。
6.  SQLite 与 MySQL 存在类型、查询、并发和迁移行为差异。若部署目标为
    MySQL，必须在专用 MySQL 测试环境验证；SQLite
    测试结果不能替代该项验收。
7.  不得把 `downgrade`
    或手工删除字段作为默认回滚方式。对不可逆迁移，应优先使用应用版本回退、向前修复迁移或经验证的数据恢复方案。

## 8. 备份与恢复

备份范围必须同时覆盖数据库和与数据库记录关联的
PDF、图片、签名等文件资产。启用个人模型时还需单独保护/备份Vault主密钥或DPAPI恢复前提，并与数据备份分开管理；没有主密钥不能声称密文配置可恢复。只备份数据库或只备份文件卷均不能保证完整恢复。

团队需确认并记录备份频率/保留期、RPO/RTO、存放位置/权限/加密/责任人、失败告警及恢复演练周期；尚未确定时标待落实。

恢复演练必须恢复到独立数据库和独立文件目录，不得覆盖正在使用的业务环境。演练应检查文献记录与文件是否匹配、关键文件哈希/可读性、用户关联、批注/笔记关联及应用实际读取。未经过恢复演练的备份不能视为已证明可恢复。

## 9. 发布、回滚与发布留痕

每次经授权发布按以下顺序：

1. 确认范围、版本身份、说明及风险。
2. 运行适用测试门槛。
3. 核对配置、迁移、文件、健康和备份。
4. 部署并执行冒烟。
5. 观察错误率、延迟和关键链路。
6. 归档实际结果和回退结论。

回滚方案必须在发布前写明，包括目标版本、执行步骤、数据库兼容性、文件格式兼容性、预计影响和负责人。应用回滚与数据库回滚必须分别设计。无法安全降级的迁移应采用前向修复或经验证的恢复方案。

发布记录至少包含版本/提交
ID、时间、变更内容、迁移版本、验证结果、已知问题、回滚版本与演练结果。应能根据版本标签找到对应的发布记录。

## 10. 性能、容量与限流

项目应通过基准测试确定列表/检索、PDF 读取、文件上传、批注保存及 AI
调用等关键操作的延迟预算、并发目标和资源上限。没有测量依据时，不得将示例阈值写成正式服务承诺。

对慢操作应记录可定位的调用阶段；对外部模型或检索等高成本接口，应设置合理的超时、并发限制和配额。超限时应返回明确错误或重试建议，不得无限等待或无限重试。应监控数据库连接、磁盘空间、文件增长和内存等容量风险。

## 11. 事件响应与安全边界

出现服务不可用、数据不一致、文件丢失、异常流量或密钥泄露时，应记录发生时间、影响范围、处置过程、恢复结果和后续改进。未经授权不得复制真实数据到个人电脑、公共日志或第三方服务。

运维脚本应默认只读或非破坏性；删除、覆盖、清空、迁移、恢复等高风险操作必须显式指定目标环境，并在执行前核对目标路径/数据库。测试与预览环境应保持数据独立，停止服务或重启服务不得被当作清理数据的手段。
