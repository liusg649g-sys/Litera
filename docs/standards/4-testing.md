## 1. 目的与适用范围

本规范用于统一 Litera
的测试设计、数据准备、执行方式、结果判定和缺陷回归要求，使测试可重复、可追溯，能够在需求或代码变化后及时发现回归问题。

本规范适用于前端、后端 API、数据库与文件存储、PDF
阅读器、认证与权限、批注、翻译、笔记，以及后续接入的 AI
问答、检索增强生成（RAG）等功能。某项功能尚未实现时，本规范规定其上线前必须满足的测试要求，不代表该功能已经完成。

本规范依据课程第七课"测试层次、用例来源、三类组织、数据隔离、一键运行、通过判定、断言有效性、缺陷判定、响应时间阈值和变更要求"等要求制定。

## 2. 基本原则与术语

1.  **先有场景，再有用例。**
    每个待交付需求至少对应一个可执行测试场景；不得只按代码函数数量编写测试。
2.  **三类用例必须覆盖。**
    每个重要功能应覆盖正常路径、失败路径和边界路径。边界路径应覆盖等价类两端及关键临界值。
3.  **失败必须可见。**
    测试失败不得被捕获后静默忽略，不得把失败用例标记为成功，也不得以跳过用例代替缺陷处理。
4.  **数据必须隔离。**
    自动化测试不得默认使用个人日常数据、真实用户资料或正在使用的本地业务数据库。
5.  **证据必须可追溯。**
    测试结论应能关联需求/场景、测试用例、执行时间、代码版本和结果。
6.  本规范中的"必须"表示强制要求，"应"表示原则上执行；例外必须记录原因、影响及批准人。

## 3. 测试分层

### 3.1 单元测试

用于验证独立函数、组件、状态转换和业务规则。重点包括参数校验、分页与筛选、阅读进度状态、批注几何数据、数据转换、错误分支及边界值。单元测试应尽量不依赖真实网络、真实模型或共享数据库。

### 3.2 接口与集成测试

用于验证前后端 API
契约、认证授权、数据库事务、文件存储与数据库的一致性、异常补偿、并发控制、迁移兼容性等。涉及数据库的测试必须明确使用的数据库类型；SQLite
通过不能自动证明 MySQL 的类型、查询、并发和迁移行为正确。

### 3.3 端到端测试

用于验证用户实际操作链路。至少覆盖注册/登录、文献上传与列表、PDF
阅读与导航、阅读进度保存、批注创建/修改/删除及导出（功能实现后）、翻译操作（功能实现后）和译文保存笔记（功能实现并验收后）。

### 3.4 数据库迁移与兼容性测试

对新增或修改的迁移，应验证空数据库升级、上一版本数据库升级、关键数据保留、索引/约束、应用读写及失败后的恢复方案。破坏性迁移不得只通过静态检查即视为验收通过。

### 3.5 AI 功能测试

AI
翻译须同时验证接口契约、错误处理、上下文与来源正确性，以及真实模型下的质量样本。Mock
只能证明调用流程和异常处理符合预期，不能证明真实模型可用性或翻译质量。未来
AI 问答/RAG 上线前，必须另建问答评测集和引用核验测试。

## 4. 场景、用例与追溯

每个重要需求应建立唯一场景编号，并维护"需求/Scenario → 测试用例 →
最近执行结果"的追溯关系。变更后应能反向查出受影响的用例。

每条用例至少记录：

- 用例编号、关联场景、模块和优先级；
- 前置条件、数据、步骤、预期与实际结果；
- 通过/失败/阻塞/跳过、环境、版本、日期及缺陷编号。

用例按以下三类组织：

- **正常路径：**
合法输入、授权用户、预期业务操作及成功持久化。
- **失败路径：**
未授权、无效输入、网络失败、数据库或文件写入失败、外部服务超时等。
- **边界路径：**
空值、最小/最大长度、文件大小临界值、页码边界、重复提交、并发冲突、过期会话及分页边界。

不能只测试"接口返回成功"。还必须检查数据库状态、文件字节、关联关系、权限边界和副作用是否符合预期。

## 5. Litera 重点测试清单

### 5.1 认证与用户隔离

-   注册、登录、退出、会话恢复、会话过期和错误凭据；
-   Origin/CSRF 等安全校验及限流；
-   用户 A 不得读取、修改或删除用户 B 的文献、批注、笔记或相关文件；
-   未授权请求应返回约定的 HTTP 状态和业务错误码，不得泄露内部异常。

### 5.2 文献管理与文件存储

-   PDF 上传、文件类型与大小校验、重复文件、损坏/加密文件；
-   题录编辑、文件夹/标签、组合检索、分页、下载、回收站、恢复及永久删除；
-   文件系统写入与数据库提交任一失败时，应验证补偿、清理或可重试行为；
-   检查文件归属、访问权限和文件内容完整性。

### 5.3 PDF 阅读与批注

-   页码、缩放、导航、搜索、阅读进度和异常 PDF；
-   文本选区、批注对象的创建/修改/删除、几何边界、页码合法性；
-   并发修改、版本冲突、幂等请求、撤销/补偿和事务失败；
-   阅读器切换文献或关闭时，旧文献上下文不得污染新文献。

### 5.4 翻译与笔记

-   手动/实时模式下的选区翻译，及连续切换选区时的触发、防抖、取消、去重和旧响应失效；未来批量追加功能另立场景，不作为现有功能；
-   校验文献
    ID、标题、文件指纹、物理页码、原文、译文、语言方向、选区定位和状态；
-   越界页码、伪造跨文献来源和不匹配文件指纹必须被阻断；已完成的历史译文可在显式确认后按原来源保存，不能一律按过期选区拒绝；
-   保存译文到新建、当前或已有笔记时，检查关联关系、重复提交、解除关联及删除行为；
-   模型失败不得返回伪造译文；来源不确定时不得伪造页码或来源说明。

### 5.5 未来 AI 问答/RAG

上线前应验证授权范围、检索结果来源、引用真实性、无检索命中、证据不足、提示词注入、跨用户数据隔离，以及模型输出不可信时的拒绝或纠错行为。

## 6. 测试数据与外部依赖隔离

1.  单元和常规接口测试应使用合成数据、临时数据库或专用测试数据库及独立文件目录。
2.  运行会清表、迁移或删除数据的测试前，必须验证目标数据库名称、主机和环境标识；不得只依赖数据库名判断安全性。
3.  测试应能重复运行；应检查随机执行顺序、重复执行及异常退出后的残留数据。
4.  测试默认不得访问生产服务、个人日常服务或真实模型。外部依赖应使用可控替身，并明确哪些测试需要真实服务。
5.  真实服务测试必须单独命名、显式启用并使用专用测试账号、数据库和文件目录。未经确认不得对当前正在使用的
    5177/5180 本地环境执行破坏性测试。
6.  测试数据不得包含真实 API
    Key、密码、会话令牌、私人文献或其他不必要的个人信息。

## 7. 断言与通过判定

每条测试必须有明确、可验证的断言。只检查"未抛异常"或"页面存在"通常不足以证明业务正确；关键场景还应检查持久化结果、权限、关联、文件完整性和失败后的状态。

-   HTTP 状态码、业务错误码和持久化状态应共同决定结果，不能把所有非 200
    响应一概视为故障。
-   对异步清理、处理中和已完成等状态，应分别定义预期语义；例如 202
    表示已接受/处理中时，不得误判为最终完成。
-   每个测试结果只能为"通过、失败、阻塞、跳过"之一。跳过必须记录原因、影响和恢复条件。
-   失败用例必须阻断相应验收；不得保留"已知失败"清单并仍宣称全部通过。
-   应对关键权限、事务、错误处理测试进行抽样变异检查：故意破坏对应逻辑后，相关测试应失败。

## 8. 统一运行、报告与发布门槛

1.  仓库 README
    必须列出前端、后端、集成、端到端及构建检查的准确命令、前置条件、退出码和报告位置。命令以当前仓库脚本为准，禁止照搬其他目录或旧版本命令。
2.  项目应提供统一测试入口或明确的分层运行清单；一次命令必须在任一必需测试失败时返回非零退出码。
3.  每次发布候选版本至少执行相关单元、接口/集成、构建及关键端到端回归；数据库变更还须执行迁移专项。
4.  报告应记录代码版本、环境、命令、开始/结束时间、通过/失败/阻塞/跳过数量及失败摘要。
5.  正向请求应设置两档响应时间阈值：目标阈值和不可接受阈值。阈值须基于固定环境与样本测量后由团队确认；课程课件中的
    50 ms/100 ms 仅为示例，不直接作为 Litera 的验收承诺。
6.  性能测试应说明请求类型、数据规模、并发数、样本数及统计口径。测试超时时间不等同于性能目标。

## 9. 缺陷管理与变更回归

缺陷记录至少包含：复现步骤、预期与实际结果、影响范围、严重程度、环境/版本、证据及关联用例。

缺陷判定区分：被错误地当作成功、被错误地放行、被错误地拒绝、应处理但未处理的故障；具体口径见第11节。

每次功能变更必须补充或调整对应场景用例；每个行为缺陷修复应先补或调整能复现该缺陷的回归用例；纯文案/规范更正用相应静态核对，不强加无关业务测试。修改接口、数据库结构、阅读器上下文或
AI 服务契约时，应检查所有相关消费者的兼容性。

## 10. 验收检查清单

-   [ ] 需求/Scenario 与测试用例可双向追溯。
-   [ ] 关键功能覆盖正常、失败和边界路径。
-   [ ] 测试数据库与业务数据隔离，清理策略明确。
-   [ ] 外部服务替身与真实服务测试边界明确。
-   [ ] 统一运行说明、退出码和报告归档可用。
-   [ ] 关键断言能在故意破坏逻辑时发现问题。
-   [ ] 缺陷修复具备回归用例，失败会阻断验收。
-   [ ] 性能阈值有测量依据和批准记录。
-   [ ] 未实现或未实际执行的测试明确标记，不虚报通过。

## 11. 缺陷判定的项目口径

Litera成功返回DTO，失败为HTTP错误+error.code；204/二进制例外，不能要求所有响应带成功业务码。被当成成功：负向请求得到成功信号或产生约定外副作用；被放行：取得越权数据/写入生效；被误拒：合法请求未得到约定结果；未处理故障：未捕获异常、回显堆栈或只有无可操作信息的通用错误。判据按2-backend与3-security，不套其他项目HTTP200包络。变异检查只在临时副本，不破坏在线服务。
