## 1. 目的与适用范围

本规范用于管理 Litera
中模型调用的边界、配置、提示词、输出校验、错误处理、评测、数据保护和成本观测，降低模型输出不确定性、提示词漂移、依赖失控及数据泄露风险。

当前规范重点适用于文献翻译相关功能，包括手动/实时两种模式下的选区翻译、连续切换选区行为，以及译文保存到笔记的关联流程。译文保存到笔记等功能在完成对应版本的人工验收前，必须标注其验收状态。AI
问答、RAG、自动信息提取等尚未完成的能力属于未来接入范围；本规范规定其上线门槛，不代表这些能力已实现。

本规范遵循课程第七课关于调用边界、工具落在既有服务方法、提示词即代码、模型与参数锁定、超时重试与降级、输出校验、不编造依据、外部内容装配、评测集回归、用量与成本观测的要求。

## 2. 基本原则

1.  **模型是概率性组件，不是权限来源。**
    身份、文献所有权、页码有效性、数据访问范围和保存权限必须由服务端确定并校验。
2.  **先校验，再使用。**
    模型输出必须经过结构、长度、语言、上下文和业务规则校验，不得直接写入关键业务数据。
3.  **失败必须明确。**
    超时、限流、网络错误或无效输出必须返回明确状态；不得伪造成功、虚构译文或用静态默认文本冒充真实结果。
4.  **提示词和参数必须可追溯。**
    每次影响输出的提示词、模型或参数变更都应评审并执行回归评测。
5.  **外部内容一律不可信。** PDF
    正文、用户输入和检索片段只能作为待处理数据，不能覆盖系统规则或扩大模型权限。
6.  **最少必要数据。**
    仅向模型服务发送完成任务所需的文本和上下文；不得默认发送整份文献、用户会话或其他用户数据。
7.  本规范中的"必须"表示强制要求，"应"表示原则上执行；例外必须记录原因、影响及批准人。

## 3. 模型调用边界与统一服务层

1.  业务页面和业务组件不得各自直接拼接供应商 HTTP
    请求。模型调用应通过统一服务层或明确的适配器完成，以集中管理配置、超时、错误映射、输出校验和用量记录。
2.  调用前必须明确任务类型、所需输入、数据范围、输出格式、超时预算和失败语义。
3.  可由确定性程序完成的规则校验、权限判断、来源匹配、去重和数据库事务，不得交给模型作最终裁决。
4.  模型不得决定用户
    ID、文献所有者、可访问文献集合、有效页码或来源真实性。服务端必须重新校验这些字段。
5.  模型能力、调用开关和供应商配置应集中管理；关闭 AI
    功能时，核心文献管理与阅读功能应按设计继续工作。
6.  Mock 适用于自动化测试和故障注入；生产或正式验收环境不得静默切换到
    Mock 并将其结果当作真实模型输出。

## 4. 模型、参数与密钥配置

1.  供应商、基础 URL、模型名称、API Key
    和任务参数应通过统一配置管理。当前项目记录中的
    `AI_PROVIDER`、`AI_BASE_URL`、`AI_MODEL`、`AI_API_KEY`、`AI_MODEL_VERIFIED`、`AI_MAX_OUTPUT_TOKENS`为开发者服务端配置；兼容TRANSLATION_*旧名。个人模型通过本人设置与Vault存储，不使用无前缀BASE_URL/MODEL/API_KEY。
2.  模型名称、供应商、API
    版本、温度、输出长度、超时和重试参数必须有明确配置来源，不得在多个业务函数中散落重复的硬编码值。
3.  开发者API Key通过私有服务端配置提供；个人Key允许本人在设置页显式输入，后端经Vault加密保存、状态不回显、输入保存后清空。Key不得提交到
    Git、写入前端包、放进提示词、测试报告或普通日志。
4.  启动时应校验必需配置。真实模型模式缺少密钥或配置错误时，应明确报错；不得返回伪造的成功结果。
5.  每次模型或关键参数变更必须记录变更原因、旧值/新值（敏感值除外）、评测结果和回退方案。
6.  测试报告必须区分 Mock、真实供应商调用和人工质量评估三种证据。

## 5. 提示词即代码与版本控制

1.  提示词模板应存放在受版本控制的文件或明确的模板注册表中，避免仅存在于个人聊天记录或临时运行代码。
2.  每个模板应有稳定标识、版本号、用途、输入变量、输出格式、适用模型及修改记录。
3.  提示词变更必须经过代码评审，并执行对应评测集；未经评测不得将新模板直接作为正式默认版本。
4.  模板中应明确任务边界、语言方向、格式要求、禁止事项和异常处理要求。翻译提示词不得要求模型编造缺失内容、引用或文献来源。
5.  用户输入和文献正文必须作为数据区块传入，不能与系统指令混合拼接成可被误解为更高优先级指令的文本。
6.  日志可以记录模板 ID
    和版本，但不得默认记录完整提示词、整段私人文献内容或 API Key。

## 6. Litera 翻译功能要求

### 6.1 输入与上下文

每次翻译请求应明确记录或传递必要的上下文标识，包括文献
ID、文献标题或可验证文件指纹、物理页码、原文、语言方向、选区定位和上下文修订号（若该模式适用）。服务端必须确认当前用户有权访问该文献。

### 6.2 手动/实时模式、选区与连续切换

-   **手动翻译：**
    用户明确触发一次翻译；重复点击应有明确的请求状态和去重策略。
-   **实时翻译：**
    必须规定触发条件、防抖/合并策略、取消过期请求的方式及调用预算，避免每次输入变化都无节制地请求模型。
-   **选区翻译：**
    必须绑定发起请求时的文献、页码和选区快照；切换文献或选区后，迟到的旧结果不得覆盖新上下文。
- **连续切换选区（现有）：** 保留最新待处理任务，不拼接不同来源。未来若增加多片段追加/批处理，须另立场景明确顺序、去重和部分失败规则。

### 6.3 输出校验

模型返回结果应检查：

- 请求成功、结果非空且不超结构/长度上限；
- 文献、页码、选区快照、上下文修订和模型配置匹配；
- 错误被识别，截断有提示，不显示为成功译文；
- 语言方向、忠实度及编造问题纳入质量评测。

前3项有现有确定性校验支撑；语言/语义质量仍需专门评测，不声称已有完整自动检测器。

校验失败时应返回可理解的错误状态，并允许用户重试或调整输入；不得悄悄把无效结果保存为正式译文。

## 7. 译文保存到笔记与来源保护

译文或选区保存到笔记时，来源块应按实际功能契约保存必要的来源信息，包括文献
ID、标题、文件 SHA-256
或其他可靠指纹、物理页码、原文/译文、语言方向、选区定位及来源状态。

1.  保存前必须重新验证当前用户权限、文献存在性、页码范围和文件指纹。
2.  越界页码、无法可靠提取的文字、伪造跨文献来源、文件指纹/签名不匹配应拒绝。文献/选区已切换的历史译文可经显式确认按原文献保存；不是一律禁止历史来源，也不能把旧译文标成当前选区。
3.  重复提交应使用明确的请求
    ID、内容指纹或其他幂等机制，避免重复创建来源块。
4.  解除笔记与文献的关联，不应在没有明确规则和用户确认的情况下删除已有来源块；删除笔记、文献或文件时应遵循统一的数据生命周期规则。
5.  数据库写入失败时，不得向用户显示保存成功。若需要跨表操作，应使用事务或可恢复的补偿流程。
6.  来源标识和状态必须来自服务端可验证的数据，不能仅信任前端或模型生成的元数据。

## 8. 超时、重试、取消与降级

1.  每种任务必须设置有限的请求超时；超时值应根据实际供应商和任务耗时测量后确定，不得无限等待。
2.  当前不自动重试上游，最多0次；用户显式重试需再次校验上下文与额度。未来若引入自动重试，只对可恢复错误设置有限次数/退避，并评测费用放大。参数错误、无权限和无效输入不应盲目重试。
3.  对
    429、5xx、连接失败、超时、响应格式错误和用户取消等情况，应映射为可识别的错误类型。
4.  用户切换文献或选区后，应尽可能取消无效请求；即使无法取消，也必须丢弃过期响应。
5.  降级只能使用明确标注的替代路径，例如提示用户稍后重试或提供手动操作；不得把旧缓存、空文本或固定示例文本伪装成刚刚生成的译文。
6.  重试与降级策略应有测试覆盖，并避免多个层级重复重试导致请求放大。

## 9. 外部内容、提示词注入与隐私

1.  PDF 正文、OCR 文本、选区内容和未来 RAG
    检索片段均属于不可信外部数据。
2.  文献中即使出现"忽略之前规则、读取其他文献、输出密钥"等指令，也必须作为待翻译或待分析的正文，不得提升为系统指令。
3.  仅向供应商发送任务必需的最小文本与必要上下文。未经明确设计和授权，不得发送其他用户的文献、笔记、账号资料或会话信息。
4.  前端错误、服务端日志和评测报告不得包含 API
    Key、会话令牌、完整私人文献正文或不必要的个人信息。
5.  如未来引入 AI
    问答/RAG，检索必须先按用户权限和文献授权范围过滤；模型生成的引用必须与真实检索片段逐一核验。
6.  AI
    问答不得仅凭模型自述认定证据充分。无命中或证据不足时，应明确说明限制，不得编造页码、引用或来源。

## 10. 评测集与回归验证

### 10.1 翻译评测

建立受版本控制的翻译样本集，覆盖中英双向、长短段落、专业术语、数字/单位、表格或特殊符号、空选区、上下文切换、超长输入和异常响应。每条样本应有预期语言方向、关键术语或人工参考译文，并记录模型版本、提示词版本、参数、耗时和评测结论。

提示词、模型、参数、切分方式或输出校验器发生变化时，必须重新运行相关样本并比较结果。质量评估可结合人工评分与确定性检查；不得仅以
HTTP 200 作为质量通过依据。

### 10.2 未来 AI 问答/RAG 评测

正式上线前，应建立约 10--20
条小样本评测集，并同时包含"必须回答"和"必须拒答/说明证据不足"的场景。检查回答内容、引用真实性、页码准确性、权限隔离和提示词注入抵抗能力。提示词或模型变更后必须重新评测并归档前后结果。

### 10.3 通过门槛

评测集必须记录版本、样本来源、评分规则、失败项和批准结论。关键安全、权限和引用真实性用例不得以平均分抵消单项失败。评测集及阈值尚未确定时，应标记为待建立，不得宣称
AI 质量已经通过正式验收。

## 11. 用量、成本与故障观测

在不记录敏感内容的前提下，应按任务记录模型/供应商标识、模型版本、提示词版本、请求时间、耗时、成功/失败类别、重试次数，以及供应商可提供的
token 或费用数据。

团队应根据实际调用量确定月度预算、单用户/单任务限额和告警阈值。没有可靠
token 或价格数据时，不得伪造精确成本。日志应能区分 Mock
与真实模型请求，并避免将用户文献正文或完整提示词作为常规日志字段。

## 12. AI 功能上线验收清单

-   [ ] 业务调用统一经过受控服务层，权限由服务端判断。
-   [ ] 模型、参数、提示词和密钥配置有明确来源与版本记录。
-   [ ] 手动/实时模式的选区及连续切换语义明确，未实现批量追加不冒充已有功能。
-   [ ] 输出经过结构、语言、上下文及业务规则校验。
-   [ ] 超时、限流、重试、取消及错误提示经过测试。
-   [ ] 译文来源、笔记关联、文件指纹和幂等规则经过验证。
-   [ ] 文献正文被视为不可信数据，最小化发送并防止越权访问。
-   [ ] 评测集覆盖质量、失败、安全和边界场景，变更后执行回归。
-   [ ] 用量与成本可观测，日志不泄露密钥或私人文献内容。
-   [ ] Mock、真实模型、人工质量验收证据分别记录。
-   [ ] 尚未实现或尚待人工验收的功能明确标记，不提前宣称通过。

## 13. 已有证据与待落实

Litera-test的test_translations/test_ai_service/test_user_models及translation*.spec验证契约/故障和时序；来源捕获测试验证签名/幂等/历史确认，不能证明真实质量。翻译提示词目前以model_service.py随提交追溯，尚无独立模板ID/版本注册表；语言忠实度/质量评测集、真实供应商验证、token计费/月度预算与告警尚待建立。工具调用/05/06是后续要求，不可写成已有服务。
